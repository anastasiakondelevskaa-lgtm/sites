# План: поднять стек с нуля на пустой ВПС

> **Статус: предложен, отмашки заказчика НЕТ.** Ни один шаг не выполняется до подтверждения.
> Документ лежит в репозитории, потому что переписка в новую сессию не переносится,
> а репозиторий переносится.

## Исходная точка — уточнена заказчиком 10.09.2026

**ВПС 37.60.234.112 (`myparser.ungurianbody.com`) пустая.** Ничего не развёрнуто, ничего не
работает, продакшена нет нигде. У нас голый каркас: код из архива есть, работающей системы нет.

**n8n не используется вообще.** Куки Instagram заказчик вытягивает из браузера сам и вставляет
в поле дашборда — зависимость от чужой машины снята целиком.

`smmparsers/README-PARSERS.md` описывает **другую** машину, существующий сервер заказчика. Как
описание этой ВПС недействителен и в работе не используется. Его ценность историческая: он
объясняет, откуда взялись куски `instagram_parser_cookies.py`.

Что это упрощает: ломать нечего, откатывать нечего, риска для живых пользователей нет.
Что это усложняет: всё, включая базовую настройку машины, делается руками с нуля.

## Задача

Три независимых компонента и общая база под ними. Формулировка заказчика: «это всё» —
лишних слоёв не строим.

| Компонент | Чем авторизуется | Что делает |
|---|---|---|
| Парсер Instagram | куки браузерной сессии, вставляются в дашборде | метрики публикаций, виральность |
| Парсер Telegram | Telethon, свой аккаунт, код из мессенджера | активность участников по ключевому слову |
| Whisper | внутренний секрет | расшифровка, **дёргаем по потребности**, не конвейером |

Общее для всех — Postgres и дашборд. Поверх базы — витрина MCP, через которую Claude читает
корпус и пишет сценарии. Дальше все прогоны идут на этой ВПС.

## Режим работы

Сессия Claude Code запущена **на Маке заказчика**, до сервера ходит по `ssh`.

**Вход по паролю не годится.** Неинтерактивный `ssh` на пароле повиснет на приглашении. Нужен
ключ, иначе автоматизация невозможна в принципе:

```bash
[ -f ~/.ssh/id_ed25519 ] || ssh-keygen -t ed25519 -C "mac"
ssh-copy-id root@37.60.234.112          # пароль спросят один раз
ssh root@37.60.234.112 'hostname'       # обязано пройти БЕЗ пароля
```

**Соединение переиспользуем** — вызовов будет много. В `~/.ssh/config`:

```
Host ung
  HostName 37.60.234.112
  User root
  IdentityFile ~/.ssh/id_ed25519
  ServerAliveInterval 30
  ControlMaster auto
  ControlPath ~/.ssh/cm-%r@%h:%p
  ControlPersist 10m
```

Дальше везде `ssh ung '<команда>'`. Скрипт из репозитория выполняется на сервере без
клонирования: `ssh ung 'bash -s' < scripts/audit.sh | tee audit.txt`.

## Порядок шагов

Каждый шаг проверяется до перехода к следующему.

**0. Инвентарь машины.** `scripts/audit.sh` — читает и ничего не меняет. На пустой машине
отработает за секунды и ответит на то, чего мы до сих пор не знаем: ОС и версия, ядра, память,
диск, что предустановлено, открытые порты, состояние `ufw`/`sshd`. От характеристик зависит
модель Whisper и число воркеров — подбирать наугад не будем.
*Бэкапа на этом шаге не требуется: сохранять пока нечего. Он становится обязательным с шага 4,
когда появляется база.*

**1. База и периметр.** Ключ SSH, смена скомпрометированного пароля, `PermitRootLogin
prohibit-password`, `PasswordAuthentication no`, `fail2ban`, `ufw` (наружу только 22/80/443),
автообновления безопасности, отдельный непривилегированный пользователь под приложения.
Всё внутреннее слушает `127.0.0.1` и наружу выходит только через nginx.

*Опасность шага:* сессия ходит по `ssh`, неверное правило экрана обрывает её вместе с доступом
к машине. Порядок жёсткий:

1. `ufw allow 22/tcp` — **до** `ufw enable`, никогда наоборот;
2. предохранитель на время правки: `echo 'ufw disable' | at now + 10 minutes`
   (снять `atrm <id>`, когда новый вход подтверждён);
3. второе окно `ssh` открыто и не закрывается, пока вход не проверен третьим;
4. `sshd -t` до всякого перезапуска демона.

Пункт 2 обязателен: он превращает ошибку из потери сервера в десять минут ожидания.

**2. Стек и периметр приложений.** nginx, TLS через certbot на `myparser.ungurianbody.com`,
Docker с compose. **Адрес один, поддоменов нет:** всё живёт на этом домене, разделы — страницами
дашборда. Один сертификат, один вход, одна точка входа снаружи.

**3. Инструментарий под правило 1.4.** `mypy --strict`, `ruff`, `pytest`, Playwright, каталог
фикстур. До него ни одна правка не сдаётся по правилам заказчика: прогона сейчас не существует.
Первые фикстуры — сохранённые страницы: рилс под живыми куками и гостевая оболочка. Без них
куки-парсер не проверяется никак, а правило 1.3 («сломай строку — тест обязан покраснеть»)
неисполнимо.

**4. Хранилище — PostgreSQL.** Решение заказчика. Разносим по схемам, чтобы три независимых
компонента не смешивались в одном пространстве имён:

| Схема | Что в ней |
|---|---|
| `core` | пользователи дашборда, задания, журнал прогонов |
| `ig` | аккаунты-цели, публикации, замеры метрик, виральность |
| `tg` | группы, прогоны, найденные сообщения |
| `media` | транскрипты с пословными отметками, классификация |

*Цена вслух.* Postgres дороже файлов: отдельная служба, память, роли, миграции, бэкап уже не
копированием файла. Взамен получаем то, чего файлами не сделать: несколько воркеров пишут
одновременно; `jsonb` под классификацию, у которой поля будут меняться; миграции как часть
сдачи. И очередь заданий делается самой базой — `SELECT … FOR UPDATE SKIP LOCKED` по таблице
в `core`, без Redis и Celery.

Доступ только с `127.0.0.1`, отдельная роль на приложение, пароль в окружении. Наружу 5432
не открывается никогда.

С этого шага заводится бэкап: `pg_dump` по расписанию, куда складывать, и **проверка
восстановлением** — бэкап, который ни разу не разворачивали, бэкапом не считается.

**5. Каркас дашборда.** FastAPI + Jinja2 — тот же стек, что в `tg-parser`: он проверен, команда
его уже видела, переиспользуются готовые решения по входу и оформлению. Вход по общему паролю
командой, `scrypt` + подписанная cookie, ограничение попыток.

Разделы — **меню слева**, у каждого своя страница: Instagram (доступ, цели, публикации),
Telegram (поиск по группе, рейтинг), Whisper (расшифровка по запросу), настройки. Один вход
на всё.

**6. Экран доступа к Instagram — куки вставляет человек.**

Заказчик берёт куки из браузера сам; дашборд обязан их принять и честно показывать состояние.
Каждое требование выведено из уже найденных дефектов, а не придумано:

*Ввод.* Одно поле, два принимаемых вида: строка заголовка
`sessionid=...; csrftoken=...; ds_user_id=...; mid=...; ig_did=...; rur=...` **и** JSON-выгрузка
браузерного расширения (массив с `name`/`value`). Второй вид нужен потому, что переносить шесть
значений руками из DevTools — почти гарантированная опечатка.

*Проверка при сохранении.* Разбираем и смотрим наличие шести обязательных имён. Чего-то нет —
называем, **каких именно**, а не «неверный формат».

*Хранение.* Fernet, ключ в окружении, файл `0600`. Значение **никогда не рисуется обратно на
экран**: только «заданы, обновлены 10.09 в 16:40» и маска хвоста `sessionid` для сверки.

*Кнопка «Проверить».* Делает настоящий запрос и отвечает одним из трёх: живы (и под каким
аккаунтом), Instagram увёл на вход — протухли, вставьте новые, либо точный текст иной ошибки.

*Индикатор в шапке дашборда.* Точка состояния и когда куки в последний раз успешно сработали.
Главный сценарий отказа — куки умирают посреди прогона; человек обязан видеть это, не открывая
логи. «Срок годности» не показываем: у `sessionid` его нет, значение имеет только дата
последнего успеха.

*Предохранитель перед прогоном.* Один дешёвый запрос до старта сбора. Куки мертвы — прогон
**не стартует** и говорит почему. Не начинаем работу, которая заведомо соберёт нули
(`almanac 3.1`, `3.2`).

*Предупреждение на экране.* Куки — живая сессия аккаунта, его могут ограничить; нужен отдельный
аккаунт под задачу, не рабочий. Так же, как `tg-parser` предупреждает про `api_hash`.

**7. Сбор Instagram и виральность.** Куки-парсер из разового скрипта — в воркера очереди:
контроль темпа, отказ вместо нулей. Закрыть `almanac 3.2` (запасной способ маскирует протухшие
куки) и `almanac 3.3` (потеря лайков на крупных числах и украинской локали). Виральность —
отношение просмотров к медиане по аккаунту, база берётся с той же страницы сетки, которая и так
грузится; абсолютные просмотры находят крупные аккаунты, а не удачные ролики.

**8. Whisper — стоит рядом, дёргаем по потребности.** Не стадия конвейера, а служба: пришёл
запрос — расшифровала, вернула, легла в `media`. Разворачивается заново и сразу без дефектов из
альманаха 6.1–6.5: слушает `127.0.0.1`, общий секрет в заголовке, `try/finally` вокруг приёма
файла, JSON на 413, один воркер на модель, `word_timestamps=True` и явный язык. Пословные
отметки обязательны: без них нельзя ответить, что прозвучало в первые три секунды, то есть
разобрать хук. Размер модели выбирается по памяти из шага 0, а не наугад.

**9. Классификация — на сервере.** Считает серверная сторона, не MCP. Поля: хук и что
прозвучало в первые три секунды, структура, хронометраж, темп речи, призыв, формат подачи, язык.
Кладётся в `media` как `jsonb` — состав полей будет меняться, и жёсткая схема тут только мешает.
*До начала шага уточнить:* провайдер и ключ. Ключ — в окружении сервера, в репозиторий не попадает.

**9а. Карточка публикации и сценарий.** Карточка показывает метрики, виральность, транскрипт и
разбор. Оттуда же — **кнопка «Запросить сценарий»**: генерация вызывается из карточки конкретной
публикации, не отдельным экраном и не пакетом. Результат хранится рядом с публикацией, чтобы
было видно, из какого образца он получен.

**10. Витрина MCP.** Только чтение корпуса: топ по виральности, транскрипт и разбор публикации,
база аккаунта. Сбор в витрину **не заводим** — он медленный и лимитируемый, ему место в фоновом
воркере.
*Цена вслух:* оркестрация — воркер по таблице заданий в `core` через `SKIP LOCKED` плюс таймеры
systemd. Ни Celery, ни Redis: очередь уже есть в базе, которую мы и так ставим. Расплата — нет
готовой панели наблюдения, как в n8n; состояние смотрим в дашборде и в журнале прогонов.

**11. `tg-parser` — на этой же машине.** Разворачивается **сразу с четырьмя правками**, а не
как есть: разделение результатов по сотрудникам (`almanac 2.5`), ключ кеша диалогов вместо
`id(client)`, кнопка CSV на серверный файл (`almanac 4.2`), срезка `100` в ссылках
(`almanac 2.3`). Ставить с известными дефектами и чинить потом — значит дважды платить.
Разделом в общем дашборде, за общим входом; собственный вход `tg-parser` при этом уходит.

## Чего не делаем без отдельного решения

- Не трогаем то, что не названо в задаче.
- Не заводим платных подписок и не подключаем внешние API без слова заказчика.
- Не открываем наружу ни одного порта, кроме 22/80/443.
- Не кладём в репозиторий ни куки, ни `.env`, ни ключи — они живут только на сервере.

## Решения заказчика — приняты 10.09.2026

1. **Классификация считается на сервере.** Не через MCP.
   *Осталось уточнить до шага 9:* какой провайдер и чей ключ. Ключ живёт в окружении сервера,
   в репозиторий не попадает.
2. **`tg-parser` разворачивается на этой же машине.**
3. **Адрес один — `myparser.ungurianbody.com`.** Поддоменов не заводим: один дашборд, разделы
   вкладками и меню слева, у каждого своя страница. Один сертификат, один вход.
4. **Отдельный аккаунт Instagram под куки заведён.** Рабочий не используется.
5. **Сценарии запрашиваются в карточке публикации** — кнопкой в самой карточке, не отдельным
   экраном и не пакетом.

Открытым остаётся только одно: характеристики ВПС, они закрываются выводом `scripts/audit.sh`
и определяют размер модели Whisper.
